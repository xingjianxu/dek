# 缓存、状态与故障恢复

dek 将“配置求值缓存（管理机）”与“已审阅计划及执行状态（目标机）”严格分离：管理机缓存可随时删除重建，而目标机状态保障了计划一致性、执行锁与故障续办能力。

## 1. 管理机：按单元的增量求值缓存

### 存储位置与特性
- 默认路径：`$XDG_CACHE_HOME/dek/<repo-id>/units/<prefix>/<unit-key-hash>.mpk`（若未设置 `XDG_CACHE_HOME`，则使用 `~/.cache/dek/...`）。
- 格式：由 Rust 核心负责读写的紧凑二进制 MessagePack 文件，提交时使用临时文件 + 单元写锁 + 原子重命名，避免并发破坏或写入中断导致损坏。
- **可随时清理**：配置仓库是唯一事实来源。你可以随时删除管理机的缓存目录，下一次规划会自动完整重建，**不会影响**目标机上仍在有效期内的已审阅计划或待恢复运行。

### 什么情况会命中 / 失效缓存？

| 场景 | 缓存行为 |
|---|---|
| 修改 `hosts/laptop/default.json`，再规划 `server` | `server` 的全部已命中单元直接复用，不启动 Ruby |
| 修改 `profiles/base.json` 中的 Git 选项 | 仅重算 `base` 及读取了 Git 选项的模块；Caddy 等无关模块继续命中展开缓存 |
| 修改通过 `source_file` 声明的 `Caddyfile` | Rust 重新计算文件摘要并比对目标机；若 Ruby 未调用 `read_text` 读取内容，则跳过 Ruby 求值 |
| 修改 Ruby `read_text` / `read_dir` / `require_relative` 涉及的文件 | 自动触发对应求值单元失效并重算（“文件不存在”也被记录为依赖，后续新建同样触发失效） |
| 修改系统环境变量 `RUBYOPT`/`RUBYLIB` 或升级 Ruby 可执行文件 | 运行时签名变化，对应 Ruby 单元自动重算 |
| 未声明 `inputs: "sdk"` 的 Ruby 单元 | 视为动态单元，每次规划都会重新求值 |
| 更新 `http_text` 外部输入 | 仅在运行 `dek refresh` 且响应内容变化时使依赖单元失效 |

## 2. 目标机：计划、内容对象与执行记录

目标端将受保护的持久化状态存放在 **`/var/lib/dek`**（本机模式可用 `--state-dir` 覆盖）：

| 存储对象 | 作用 |
|---|---|
| 已审阅计划（`plans/<plan-id>.mpk`） | 绑定仓库 ID、逻辑主机名、目标主机标识、有序动作、依赖边、变更原因、内容摘要、包候选与前置条件 |
| 内容对象（按 SHA-256 寻址） | 固化审阅时刻的静态文件、unit 定义、公钥与密文字节；执行已审阅计划时严格使用此内容 |
| 执行记录（按 `run_id` 索引） | 记录每次运行的每个动作结果（`已核验`、`失败`、`结果待核验`、`待激活`、`待执行`）以及待重试服务通知 |
| `age` 验证标记（`secrets/`） | 权限 `0700`，保存随机 HMAC 密钥与各密文落点的验证标记（不含明文） |
| 目标执行锁 | 保证同一目标机上的规划保存、过期回收与 `apply` 串行执行，避免并发写入冲突 |

### 计划有效期与回收策略（`retention.json`）

- **默认有效期**：已审阅计划默认保留 **7 天**（604,800 秒）。
- **自定义保留时长**：在目标状态根目录（默认 `/var/lib/dek/retention.json`）创建文件，归目标端运行账户所有且权限为 **`0600`**，指定正整数 `planTtlSeconds`：
  ```json
  {
    "planTtlSeconds": 259200
  }
  ```
- **自动回收与引用保护**：
  - 每次在目标端保存新计划时，在状态锁内自动回收已过期的计划以及不再被引用的内容对象。
  - 仍处于有效期内的计划，以及**任何尚未完成或待恢复执行所引用的计划和内容**，都会被强制保留，绝不会在续办前被误删。
  - 计划过期后若尝试用旧 ID 执行，目标端会明确报告过期并要求重新运行 `dek plan` 获取新计划 ID。

## 3. 幂等性保证与前置条件校验

- **相同配置重复应用**：对可核验的受管资源，应用成功后若期望状态未变且目标无漂移，再次运行 `dek plan` 应输出 `已符合声明，0 项变更`，运行 `dek apply` 应报告 `已核验完成，实际变更 0 项`。
- **计划固化语义**：如果你在 `dek plan` 之后又编辑了仓库中的 `Caddyfile`，执行原 `dek apply --plan <旧ID>` 仍会严格写入审阅时固化的旧内容（前提是目标机前置条件仍满足）；想发布新修改请重新运行 `dek plan`。
- **前置条件冲突**：执行前若发现目标文件被人改过、包版本发生变化或依赖条件不再满足，dek 会中止冲突动作并给出原因或生成替代计划供重新审阅。

## 4. 服务通知合并、失败重试与续办

### 通知合并与去重
- 同一次执行中，多个文件或资源触发同一个 systemd 服务的通知会自动合并为一次动作。
- 如果服务在本次执行中是首次启动（且已经加载了新配置），自动省略多余的 `reload`。

### 失败恢复与待续办通知
- 在替换目标文件之前，目标端就会先登记对应的待执行服务通知。
- 即使文件替换成功但随后 `systemctl reload` 失败（例如配置语法问题或临时故障），目标端仍会保留这条**待续办服务通知**：
  - 下一次运行 `dek status` 或 `dek plan` 时，即便文件内容已经一致，输出末尾也会显式列出 `待续办 [...] 重载服务 ...，执行 <run-id>`。
  - 修复问题后运行 `dek apply -H <host> --run <run-id>`（或直接 `dek apply -H <host>`）即可补完未完成的服务重载。
- 若某个动作因意外中断导致结果无法确定（`结果待核验`），续办时会先重新观测目标实际状态：已满足则标记核验完成；仍无法确认时保留原记录和诊断，暂停自动盲目重试，待人工核查。
