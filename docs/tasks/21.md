# #21 以双主机示例验收阶段②的缓存命中和局部失效

[GitHub Issue #21](https://github.com/xingjianxu/dek/issues/21) · Task

- 分支：`issue-21-accept-incremental`
- Worktree：`/data/dek-dev/worktrees/21-accept-incremental/`

## 交付目标

从公开 CLI 验证两台主机共享 profile 时的 Ruby 启动次数、失效范围和实际计划差异。

## 范围与接口

在 `crates/dek-cli/tests/` 以独立临时仓库和缓存目录运行 CLI，复用具备文件及服务观测的测试后端。记录单元命中和实际 Ruby 子进程启动计数。

设计位置：[docs/design.md](../design.md) §4.2、§7.2、§8、§9.1。

直接前置：[#19](19.md)、[#8](8.md)、[#16](16.md)、[#20](20.md)。

## 实施步骤

1. 准备 laptop、server、公共 profile、启用 Caddy 的声明、静态 Caddyfile 和已标记/未标记的 Ruby 单元，对无变更目标建立可重复基线。
2. 分别采集冷启动、跨主机热规划、修改单个入口、修改公共 Git 选项、修改静态 Caddyfile 的计划与计数。
3. 对相同临时目标手工改变受管状态，并运行原生 I/O 夹具，校验目标漂移与求值缓存策略各自反映在结果中。

## 验收条件

- [x] 暖好 server 的可缓存路径，仅改 laptop 后再运行 `dek plan -H server`，Ruby 启动数为 0，计划与先前相同。
- [x] 在已应用的 Caddy 基线上只改 Caddyfile，计划仅包含相应文件更新及服务通知。再改公共 Git 选项，两个 host 获得新 Git 值且 Caddy 展开继续命中。
- [x] 清除所有受管差异后在目标上手工改文件，热缓存规划仍检出差异。未标记的原生 I/O 单元跨运行重新求值，标记为 SDK 且输入未变的单元继续命中。

## 验证记录

运行 `cargo test --locked -p dek-cli --test planning incremental:: -- --nocapture`。每次规划在独立进程中执行 CLI 命令，注入现有文件及服务测试后端。目标文件存放在夹具目录，由测试设置已收敛基线和手工漂移。Ruby 包装器统计实际进程启动，缓存记录的原子替换用于确定重建范围。

| 场景 | Ruby 启动 | 写入的求值记录 |
|---|---:|---:|
| server 冷启动 | 1 | 9 |
| laptop 首次规划，复用公共 profile | 0 | 8 |
| server 热规划或 laptop 入口变更后规划 server | 0 | 0 |
| 规划已编辑入口的 laptop | 0 | 3 |
| 只改 Caddyfile 或在目标上手工改 Caddyfile | 0 | 0 |
| 公共 Git 选项变更后规划 server / laptop | 1 / 0 | 3 / 2 |

Git 变更仅写入公共 profile、两台主机的合并和 Git 展开记录。原生 I/O 通过实际 `dek show` 进程验证，连续读取均启动 Ruby 且读到手工更新后的值。SDK 输入保持不变时复用其采集记录。
