# #28 恢复部分完成的执行并通过 status 查询结果

[GitHub Issue #28](https://github.com/xingjianxu/dek/issues/28) · Feature

- 分支：`issue-28-recover-runs`
- Worktree：`/data/dek-dev/worktrees/28-recover-runs/`

## 交付目标

让用户根据 run_id 找出已完成、失败、结果不明和待重试动作，重发相同请求时可安全恢复。

## 范围与接口

在 dek-target::executor 使用目标运行记录接口执行恢复判断，在 dek-cli 接入 status [-H 主机] [--run ID] 与 --json。

设计位置：[docs/design.md](../design.md) §3、§4.2–4.3、§5、§6、§7.2、§8③–⑤。

直接前置：[#27](27.md)。

## 实施步骤

1. 将请求标识与 run_id 对应，记录动作调用前状态、后端结果、重新观测结果和剩余依赖；查到同一请求时复用已有结果。
2. 为已完成、已知失败与结果不明的动作分别处理重试。恢复先重读实际状态，无法确认包事务或重启结果时保留诊断，并向用户呈现下一步所需信息。
3. 让 status 默认展示该主机最近一次执行，按 ID 展示指定执行，文本和 JSON 均包含可定位的资源、已完成、失败与待重试项。
4. 让后端可将未执行的服务通知带入下一次规划，恢复过程只使用目标端保存的上下文。

## 实现与验证

`dek status -H <主机> [--run <执行ID>] [--json]` 读取目标记录。普通 `apply` 会提示续办最近一次未完成的审阅执行，`apply --run` 可指定执行。脚本可用 `apply --plan <计划ID> --request-id <标识>` 重发同一次请求。

恢复沿用冻结计划、已校验对象及原尝试记录。若一次写入的效果已经满足，复查后仍使用原尝试号登记核验。包事务和服务效果缺少可确定的结果时保留诊断。计划展示仍在目标记录中的服务通知，其执行 ID 指向原续办上下文。[执行恢复决定](../adr/28-run-recovery.md)

运行 `cargo test --locked -p dek-cli --test apply`。模拟后端覆盖部分完成、实际进程中断、包事务结果不明、缓存清除和归属检查。按 [#27](27.md) 的探针编译方式将 `CARGO_TARGET_DIR` 改为本任务目录，通过 `scripts/tests/local-apply` 在普通 Arch 来宾账户复核。

## 验收条件

- [x] 注入两动作执行，第一项成功、第二项失败。运行 status --run <ID> --json 能对应到两项结果，再次 apply 只补完第二项。
- [x] 让后端完成一次动作后在回写结果前中断，恢复时观测计数先增加。已达成的动作不会重复写入，无法判断的非幂等动作保留为结果不明。
- [x] 重复提交相同请求标识，得到原 run_id 和已有结果。清除管理机求值缓存、重启 CLI 后，status 仍可查询相同结果。
- [x] 为同一主机连续执行两次，status 指向较新 run，--run <旧ID> 返回旧记录。用另一主机查询该 ID 时返回归属错误或未找到。
