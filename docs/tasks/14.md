# #14 按目标能力与实时观测生成带前置条件的执行计划

[GitHub Issue #14](https://github.com/xingjianxu/dek/issues/14) · Feature

- 分支：`issue-14-target-planner`
- Worktree：`/data/dek-dev/worktrees/14-target-planner/`

## 交付目标

让目标端以可注入的后端验证整份资源清单，按实际差异生成带原因、先后顺序及绑定的计划。

## 范围与接口

在 `crates/dek-target` 的 `backend` 定义可注册的能力、路径同一性、校验、观测、规划、执行与核验接口，在 `planner` 实现只读规划并用小型测试替身验证。实际 Linux 后端、文件或计划存储、执行调度另行交付。

设计位置：[docs/design.md](../design.md) §1.1、§3、§4.3、§8、§9。

直接前置：[#3](3.md)。

## 实施步骤

1. 由后端上报目标标识、系统、发行版、架构、版本化资源类型及支持属性。让目标端规范化原始目标路径并检测别名冲突。
2. 在产生可执行计划前校验整份清单，缺失能力、未知属性或冲突均报目标主机与配置来源。只记录此次使用的能力、兼容版本与事实。
3. 按当前实际状态生成有序类型化动作及其原因、依赖和前置条件，对已满足或停止管理的资源跳过动作，输出目标绑定及资源摘要。
4. 给执行端提供原计划已用能力/后端版本的兼容性复核入口，可在每次规划重新读取实际状态。

## 实现落点

- `dek_target::backend::BackendRegistry` 注册目标身份、能力及路径同一性函数。`dek_target::planner::plan` 先校验整份清单，再调用后端观测和生成动作。
- `check_compatibility` 复核计划的目标与所用能力。[目标端规划的能力记录与顺序](../adr/14-target-planning.md)记录版本、路径、动作和通知的约定。

## 验收条件

- [x] 注入仅有可观察文件的测试后端，先置相同内容得到 0 项，再只改变后端实际文件，使用同一 `ResourceSet` 重新规划得到单项文件动作及原状态前置条件。
- [x] 在包含合法文件的清单追加一条后端不支持的服务资源，再测试不支持的文件属性，均报告主机、缺失能力及声明位置，均不返回部分可执行计划。
- [x] 用同一后端测试中有先后依赖的两个资源，计划内依赖先于使用者。删除声明后不产生隐式移除动作。
- [x] 给测试目标新增无关能力，旧计划的兼容性检查通过。将旧计划所用后端换为不兼容版本，检查拒绝该计划并标明具体能力。

`./scripts/check` 通过。内存后端另验证了路径别名、缺失依赖、循环、服务通知和首次启动顺序。
