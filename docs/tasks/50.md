# #50 在 Arch 虚拟机验收补装、升级审批与部分失败恢复

[GitHub Issue #50](https://github.com/xingjianxu/dek/issues/50) · Task

- 分支：`issue-50-arch-upgrade-acceptance`
- Worktree：`/data/dek-dev/worktrees/50-arch-upgrade-acceptance/`

## 交付目标

用实际 pacman、paru、systemd 和 CLI 重现阶段⑤的审批、事务漂移和失败续做行为。

## 范围与接口

在 dek-cli 的 Arch 虚拟机集成用例准备仓库包、AUR 构建和服务夹具，复用现有 VM 生命周期，记录每个场景的前后状态。

设计位置：[docs/design.md](../design.md) §6、§7.2–7.4、§8⑤、§10.6、§10.8、§11。

直接前置：[#49](49.md)、[#23](23.md)、[#33](33.md)。

## 实施步骤

1. 复用上游包事务预览卡确认的测试网络策略和受控软件源，在实机记录官方仓库、AUR 输入与所用缓存。
2. 准备可重复切换的仓库候选和 AUR 版本，分别运行普通补装、需整机升级的补装、主动 upgrade 与通过 plan_id 执行。
3. 在计划和应用之间改变候选版本或扩大范围，再注入可恢复的 AUR 编译失败和一次服务 reload 失败。保存各次 run_id、包数据库查询、服务计数和恢复后的 CLI 输出。

## 验收条件

- [ ] 独立补装场景验证声明包与依赖就绪。需整机升级的场景在首次 apply 返回 plan_id 后校验系统包、配置、服务均未改动，按 ID 确认后才开始执行。
- [ ] 修改候选版本或事务范围后，执行旧 plan_id 得到新 ID，已安装版本维持旧值。用新 ID 执行后实际包集与批准清单一致。
- [ ] 仓库包升级完成后制造 AUR 构建失败，status 定位失败包，修复并重试时无需再执行仓库事务。独立注入 reload 失败，文件内容已一致的下一次 apply 仍能补完通知。
- [ ] 将 PR 的实机证据关联至 fixture 版本、基础镜像标识和网络条件，可在新差分盘重跑得到相同断言。

提交与 PR 验证按[协作约定](../../AGENTS.md)执行。
