# #43 通过 SSH 执行计划并在断线后查询与续办原运行

[GitHub Issue #43](https://github.com/xingjianxu/dek/issues/43) · Feature

- 分支：`issue-43-ssh-apply-resume`
- Worktree：`/data/dek-dev/worktrees/43-ssh-apply-resume/`

## 交付目标

让用户能按同一 run_id 找回远端执行结果，并在断线、响应丢失与重复请求后安全完成剩余动作。

## 范围与接口

在 `dek-cli`、`dek-controller::transport` 和 `dek-target` 适配 `apply`、`apply --plan` 与 `status [--run] [--json]`。复用本机执行器的锁、冲突检测、结果核验、恢复及服务通知逻辑。

设计位置：[docs/design.md](../design.md) §4.3、§5、§6、§7.2、§7.3。

直接前置：[#42](42.md)、[#28](28.md)、[#27](27.md)。

## 实施步骤

1. 对当前目标发起稳定标识的执行请求，开始执行时输出 `run_id`。普通 apply 和按 ID 执行使用对应计划及其固化内容。
2. 重连先重新核对目标并查询原运行。重复发送相同请求要返回已有结果或接续仍待办的动作。对结果不明的步骤交由目标执行器重新观测。
3. 连接中断、计划失效及范围扩大分别返回可采取的下一步。需要重新审阅时向用户展示新计划 ID。支持按目标查最近执行及按 ID 查指定执行。
4. Ruby 由管理机普通用户运行，目标段按动作需要提权。sudo/helper 的交互提示使用独立终端通道，使结构化结果可解析。

## 实现与验证

`dek apply -H <host> [--plan <ID> --request-id <标识> | --run <ID>]` 和 `dek status -H <host> [--run <ID>] --json` 适用于 SSH 目标。目标登录账户持有私有状态目录，默认 `/var/lib/dek`。已审阅动作所需交互终端可通过 `--interactive` 启用。[执行与终端决定](../adr/43-ssh-execution-and-terminal.md)

运行 `./scripts/check` 验证 CLI、运行记录、重发和绑定场景。按 [#27](27.md) 先构建 Arch ABI 的 `apply` 测试包，再构建 Arch ABI 的目标端 `dek`，并为管理机本机构建一次 `dek`。用两台 [Arch 来宾](23.md) 运行以下命令。

```bash
scripts/tests/ssh-apply-resume v20261115.625457 \
  "$CARGO_TARGET_DIR/debug/dek" "$CARGO_TARGET_DIR/x86_64-unknown-linux-gnu/debug/dek" "$probe"
```

实机验收使用真实 OpenSSH 和两个独立的 Arch 状态根。包操作、故障服务和交互 helper 使用同一测试后端，调用次数与执行记录由脚本核对。

## 验收条件

- [x] 在测试执行器已提交包操作结果、管理端尚未收到回复时切断连接。重发同一请求只得到同一 run_id 和结果，包操作调用次数为 1。
- [x] 断线时目标记录一项结果不明的动作。重连查询可见该状态，继续时先观测。模拟服务首次失败，后续仅处理待办服务，最近和指定 run 的 JSON 均可解析。
- [x] 对同一目标同时发起两次不同的 apply，观测两次目标变更的临界区不重叠。把同一计划 ID 用于另一目标被拒绝。
- [x] 用测试 sudo/helper 向独立终端读取一次输入，管理机收到完整结构化结果，诊断和交互内容均未混入协议响应。
