# #24 在目标机保存已审阅计划及其引用的文件内容

[GitHub Issue #24](https://github.com/xingjianxu/dek/issues/24) · Feature

- 分支：`issue-24-target-plan-store`
- Worktree：`/data/dek-dev/worktrees/24-target-plan-store/`

## 交付目标

使本机 `dek plan` 返回的 ID 能在目标端读取同一份版本化计划及审阅时的文件字节。

## 范围与接口

在 `dek-target::state` 实现受保护的计划和按摘要寻址的内容存储，在本机 `dek-cli` 规划入口装配。对 `ResourceSet` 和 `Plan` 复用核心类型。对接执行器的接口返回经校验的计划与对象。

设计位置：[docs/design.md](../design.md) §3、§4.3、§5、§7.2、§9。

直接前置：[#16](16.md)、[#23](23.md)。

## 实施步骤

1. 实现按摘要检查、补入与读取内容对象的接口。写入时验证实际字节摘要，多个计划可引用同一份已校验内容。
2. 在可信目标端写入 `/var/lib/dek/plans/<plan-id>.mpk` 版本化记录，固化仓库与目标身份、资源摘要、动作顺序及原因、前置条件、文件引用及包候选。先准备内容，再发布可完整读取的计划。
3. 从本机 `plan` 接入存储，使响应、终端与 JSON 中的 ID 指向同一计划。按目标权限和归属读取，拒绝不支持的版本或未知动作、错误仓库/目标及缺失对象。
4. 验证计划目录和内容目录仅由受信任目标端进程写入。读取或写入失败时指出对象与后续重新规划入口。

## 使用

Linux 本机 `dek plan --json` 在返回 ID 前保存计划与内容。默认状态根为 `/var/lib/dek`。首次部署时由管理员运行 `sudo install -d -m 0700 -o <可信目标账户> /var/lib/dek`，然后以该账户运行 `dek plan`。也可传入 `dek plan --state-dir <绝对路径>` 使用该账户的私有状态目录。观测和 Ruby 求值使用调用者权限。

状态根下的 `plans/<plan-id>.mpk` 包含完整资源集合与核心计划，`objects/<SHA-256 十六进制>` 保存原始内容。使用 `dek_target::state::StateStore` 加锁并按仓库、清单主机名、目标身份读取。格式与权限约定见 [ADR](../adr/24-target-plan-storage.md)。

## 验收条件

- [x] 在隔离状态目录运行本机 `plan --json`，按输出 ID 读取磁盘记录。动作、顺序、内容摘要与输出一致。改管理机源文件并清空求值缓存，旧 ID 仍解析为当时审阅的字节。
- [x] 两个计划引用同一内容时只存一份。故意提交摘要与字节不符的对象，存储拒绝发布引用无效内容的计划。
- [x] 用不同目标或仓库读取旧 ID，再分别测试未知动作和删除所引用内容。均返回可定位错误，受管状态无写入。
- [x] 在隔离目标上让无权账户尝试覆盖计划和内容对象，写入均失败，原计划仍能完整读取。

运行 `./scripts/check` 验证记录、内容、身份绑定、版本错误与源文件更新后的旧计划读取。Arch 实机用 #23 的运行脚本部署当前构建，通过 `scripts/run-arch-vm ssh <轮次> bash -s < scripts/tests/target-plan-store` 验证默认路径。来宾需提供 Ruby。该用例使用全新来宾，以普通账户规划并由另一 UID 尝试改写两类文件。
