# #5 从静态 JSON 采集赋值并展开主机引用的 profile

[GitHub Issue #5](https://github.com/xingjianxu/dek/issues/5) · Feature

- 分支：`issue-5-json-profile-graph`
- Worktree：`/data/dek-dev/worktrees/5-json-profile-graph/`

## 交付目标

从选中的主机入口按需得到带来源的赋值与完整的 profile 引用图。

## 范围与接口

在 `crates/dek-controller` 的 `eval`/`repo` 实现原生 JSON 采集器和与语言无关的图遍历。配置语言适配器可注入，Ruby 进程、合并规则及跨运行缓存另行接入。

设计位置：[docs/design.md](../design.md) §2、§2.1、§2.2、§3、§3.1、§4.2。

直接前置：[#2](2.md)、[#4](4.md)。

## 实施步骤

1. 解析含 `schemaVersion`、`imports`、`options` 的静态单元，在每条赋值和导入处记录文件及 JSON Pointer，并记录入口依赖。
2. 由 Rust 按清单名称解析 profile，从所选 host 展开嵌套引用。使用规范化参数区分单元，相同引用和参数可复用本次计算。
3. 按引用路径诊断未知 profile、循环引用、格式版本错误或非法字段类型，为 host 和 profile 附加后续合并所需的层级信息。

## 验收条件

- [x] 让两个 host 各引用 `base`，只规划其中一个的声明图，结果包含其入口及 `base`，另一主机的故意损坏入口不参与读取。
- [x] 在测试中让两个引用用不同键顺序传入等值参数，再传入不同参数。前两者得到同一单元，后者得到独立单元。
- [x] 令 `base` 引用 `extra`、`extra` 再引用 `base`，诊断给出导入链和引用位置。将引用改成未知名，诊断指向该处 JSON Pointer。
- [x] 使用纯 JSON 仓库并将 Ruby 移出测试 `PATH`，静态采集成功。将 `schemaVersion` 改为不兼容值后输出入口位置与版本错误。

`cargo test --locked -p dek-controller --test json_profile_graph` 复现这些场景，并检查入口摘要、字段类型、来源和采集器注入。
