# #45 用隔离的软件源数据预览完整的 Arch 滚动升级

[GitHub Issue #45](https://github.com/xingjianxu/dek/issues/45) · Feature

- 分支：`issue-45-arch-upgrade-plan`
- Worktree：`/data/dek-dev/worktrees/45-arch-upgrade-plan/`

## 交付目标

让 dek plan --upgrade 和需要整机升级的补装返回完整的可审阅事务及 plan_id。

## 范围与接口

在 dek-linux::arch 构建仓库事务预览，在 dek-target::planner 合并受管 AUR 构建目标与可预见的配置动作，在 dek-cli 接入 plan --upgrade 和 --json。

设计位置：[docs/design.md](../design.md) §4.3、§6、§7.2–7.4、§8⑤、§11。

直接前置：[#38](38.md)、[#16](16.md)、[#24](24.md)。

## 实施步骤

1. 在首次使用包源的集成用例编码前按 §11 确认网络策略。在本 Issue 记录官方包与 AUR 源码分别使用的离线镜像、代理缓存或按用例开放的网络，记录可复现的输入和验证方法。
2. 通过目标 pacman 配置与独立临时数据库获取预览所需的仓库元数据，检测软件源不可达等无法可靠预览的情形。
3. 识别需刷新元数据、已单独刷新数据库且有待升级包、补装与当前系统一致性无法确认三种情况，均转入完整升级预览。
4. 列全新增、升级、替换、移除的仓库包，包括尚未被 dek 声明但会参与的已安装仓库包，并为受管 AUR 候选保留明确的构建清单。
5. 把候选版本、范围、可预见配置动作和前置条件写入同一计划，输出可直接传给 apply --plan 的 ID。规划失败时明确列出缺失信息。

## 使用和验证

`dek plan --upgrade -H <主机> --json` 返回持久化的 `plan_id`、原生仓库事务、受管 AUR 目标和可预见的配置动作。文本预览展示同一份清单。普通 `apply` 发现补装需要整机升级时，会输出计划及 `dek apply -H <主机> --plan <计划ID>` 命令，等待审阅。仓库隔离与候选绑定见 [原生事务预览 ADR](../adr/45-isolated-arch-upgrade-preview.md)。

用 `scripts/tests/arch-upgrade-plan <镜像标识> <Arch 兼容的 dek 构建>` 运行验收。脚本传入开发机已有的 Ruby Nix 闭包，在外网关闭的 Arch 来宾生成 A/B 两套本地仓库，记录输入 SHA-256、文本和 JSON 一致性以及每次规划前后的包数据库、受管文件与服务摘要。管理端还通过同一来宾的 SSH 接口核对普通规划和显式升级规划。构建和安装使用来宾原生 `repo-add`、`pacman` 与 `libalpm`。受管 AUR 目标使用离线声明和已安装版本，源码查询与签名验证由后续任务验收。 [测试软件源策略](https://github.com/xingjianxu/dek/issues/45#issuecomment-7086772680)

## 验收条件

- [x] 用两套可切换的测试源状态预览，终端与 JSON 的新增、升级、替换、移除清单一致，包含受影响的非受管仓库包。查询系统同步数据库摘要与受管文件显示均未改动。
- [x] 分别模拟需要刷新、刚单独刷新且系统有更新、兼容性未知。每种情况调用普通 apply 都先返回完整升级计划 ID，包数据库、配置文件和服务状态均保持。
- [x] 让预览所需软件源不可用，错误指出缺失的仓库数据，系统主数据库保持原摘要。
