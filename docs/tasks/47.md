# #47 经确认执行完整 pacman 升级并复核后续配置

[GitHub Issue #47](https://github.com/xingjianxu/dek/issues/47) · Feature

- 分支：`issue-47-arch-upgrade-apply`
- Worktree：`/data/dek-dev/worktrees/47-arch-upgrade-apply/`

## 交付目标

让 dek upgrade 和 apply --plan 只执行用户审阅的完整包事务，升级后将计划外配置变化交还审阅。

## 范围与接口

在 dek-cli 实现 upgrade 的交互确认与非交互输出，在 dek-linux::arch 和 dek-target::executor 复核并执行完整仓库事务。

设计位置：[docs/design.md](../design.md) §4.3、§5、§6、§7.2–7.4、§8⑤。

直接前置：[#45](45.md)、[#28](28.md)。

## 实施步骤

1. 交互终端展示完整清单并等待确认，非交互模式返回待审阅计划，普通 apply 触发升级时提示带主机参数的 apply --plan 命令。
2. 在目标锁内重算包事务与候选版本，按原计划的仓库和主机绑定校验。范围或版本有变时保存并展示新计划。
3. 确认后按一次完整 pacman 事务完成仓库升级与缺包补装，从本地包数据库核验并记录结果，再调用适用的受管 AUR 阶段。
4. 包升级完成后复核配置，按计划执行预见到的动作。产生计划外新动作时返回新计划，保留已完成事务。

## 验收条件

- [x] 在伪终端取消确认以及无终端运行 upgrade，均可得到审阅信息，已安装版本与配置保持不变。用确认后的计划 ID 执行时输出 run_id。
- [x] 记录升级调用，确认一次 pacman 事务同时完成已安装包升级与缺包补装。更换测试源的候选版本或新增被替换的包后执行旧计划，返回新 ID 且没有包被升级。
- [x] 构造包升级后突然出现的配置动作，命令返回新计划，并可通过 status 查到已完成的包事务；新动作在得到确认前未执行。

## 使用与验证

`dek upgrade -H <主机>` 显示已保存的完整升级计划。输入和输出均接入终端时，输入 `y` 或 `yes` 确认。非交互模式返回待审阅计划和带主机名的执行命令。显式 `dek apply -H <主机> --plan <计划ID>` 使用同一复核与执行路径。目标端执行包事务需要 root 权限，远程模式在管理机完成求值。

包事务完成后出现新的配置动作时，命令返回后续计划 ID，`dek status -H <主机> --run <执行ID> --json` 保留包事务的核验结果及 `replacement_plan_id`。审阅后用新 ID 继续配置。签名、软件源、锁和异常恢复见[全量事务决定](../adr/47-reviewed-arch-upgrade.md)。

运行 `./scripts/check` 和隔离 Arch 验收。按 [#40](40.md) 构建管理机与 Arch ABI 两份二进制。

```bash
scripts/tests/arch-upgrade-apply v20261115.625457 \
  "$CARGO_TARGET_DIR/debug/dek" "$CARGO_TARGET_DIR/x86_64-unknown-linux-gnu/debug/dek"
```

实机脚本在离线来宾创建并签名三套文件仓库。它验证伪终端取消、非交互预览、审阅过期、候选变化、本机单次包升级和补装、配置再审阅、同一请求重放及 SSH 已审阅执行。
