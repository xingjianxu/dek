# #16 用 dek plan 展示目标差异并验证 JSON 与 Ruby 计划等价

[GitHub Issue #16](https://github.com/xingjianxu/dek/issues/16) · Feature

- 分支：`issue-16-cli-plan`
- Worktree：`/data/dek-dev/worktrees/16-cli-plan/`

## 交付目标

让同一主机的 JSON 与 Ruby 写法经过同一条本地规划链路，得到可审阅且语义相同的计划。

## 范围与接口

在 `crates/dek-cli` 接入普通 `plan`，在 `examples/minimal` 和 CLI 集成测试提供等价配置及可注入的本地后端。接入目标返回的计划 ID，生产目标计划持久化、SSH、升级及执行子命令由后续 Issue 装配。

设计位置：[docs/design.md](../design.md) §3、§4.3、§7.1–7.3、§8 阶段①。

直接前置：[#15](15.md)、[#14](14.md)、[#13](13.md)、[#12](12.md)、[#8](8.md)。

## 实施步骤

1. 将主机选择、求值、schema 合并、资源展开、静态文件内容处理与目标规划串联，适配本机目标调用，允许测试注入已知观测。
2. 实现 `dek plan [-H/--host <主机>] [--repo <目录>] [--json]` 及帮助。文本和 JSON 从同一 `Plan` 输出目标、`plan_id`、动作、原因与前置关系。
3. 为 JSON 与 Ruby 主机入口建立等价的混合 profile、Caddy 静态文件及真实源位置的测试。规划失败返回非零，CLI 不执行目标变更。

## 实现落点

- `dek plan` 与 `dek show` 复用仓库发现、主机选择、声明采集与合并。本机规划将展开后的资源交给目标端，全程只调用观测与规划接口。
- 本阶段生产本机后端提供文件观测，内存后端用于验收 Caddy 的包、文件与服务完整链路。JSON 输出将目标给出的 ID 写为 `plan_id`，与文本展示相同的计划与动作。
- [最小示例](../../examples/minimal/dek.json)中的 `server` 与 `server-ruby` 共享 JSON profile 和 Caddyfile。

- [本机规划决定](../adr/16-local-plan-command.md)记录了计划 ID、绑定与 JSON 形式。

## 验收条件

- [x] 用同一个内存目标状态分别执行 JSON 和 Ruby 入口的规划，比较去除运行标识及语言来源后的选项、资源、动作、原因与顺序，各阶段均相同。
- [x] 执行 `dek plan --repo <仓库> -H server --json`，输出可解析且有目标返回的 `plan_id`。文本展示相同动作。把已部署 Caddy 的源文件改动后得到更新文件与通知服务的原因，后端变更调用次数为 0。
- [x] 对已匹配声明的目标再运行普通 `plan`，得到 0 项变更。依次注入未知 option、类型错误和同级冲突，均报相关文件及行号或 JSON Pointer，完全不生成可执行计划。
- [x] 从源码目录以外运行已安装的 CLI，Ruby 求值器能按发行包内位置加载。仅用静态 JSON 时即使 PATH 中没有 Ruby 也可求值。

`./scripts/check` 通过。使用 `cargo install --locked --offline --debug --path crates/dek-cli --root <临时目录> --bin dek` 安装后，从仓库外运行该二进制。Ruby 入口输出文件变更并保留目标文件，JSON 入口在空 `PATH` 下输出零项变更。
